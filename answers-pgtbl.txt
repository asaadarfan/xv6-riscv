CS311 Assignment 3, Task 1: xv6 page tables lab (pgtbl)

Permission bits used below (low 10 bits of a PTE):
  V=0x01 valid, R=0x02 read, W=0x04 write, X=0x08 execute, U=0x10 user,
  G=0x20 global, A=0x40 accessed, D=0x80 dirty.
A and D are set by the hardware (QEMU) when the page is first accessed /
written; xv6 itself never sets them.

Layout of the pgtbltest binary (riscv64-linux-gnu-readelf -l user/_pgtbltest):
  LOAD 0x0000  filesz 0x158c  R E   -> text + rodata, pages 0x0 and 0x1000
  LOAD 0x2000  memsz  0x30    RW    -> data + bss, page 0x2000
exec() then adds a guard page and USERSTACK (= 1) stack page above that,
so the process size is 0x5000.


============================================================
1. Inspect a user-process page table
============================================================

Output of print_pgtbl (from the final kernel, i.e. after "speed up
getpid", which is why USYSCALL at 0x3FFFFFD000 is mapped; in the
unmodified kernel that entry was 0):

va 0x0 pte 0x21FDF85B pa 0x87F7E000 perm 0x5B
va 0x1000 pte 0x21FDEC1B pa 0x87F7B000 perm 0x1B
va 0x2000 pte 0x21FDE817 pa 0x87F7A000 perm 0x17
va 0x3000 pte 0x21FDE407 pa 0x87F79000 perm 0x7
va 0x4000 pte 0x21FDE0D7 pa 0x87F78000 perm 0xD7
va 0x5000 pte 0x0 pa 0x0 perm 0x0
...       (0x6000 - 0x9000 identical: pte 0x0)
va 0x3FFFFF6000 pte 0x0 pa 0x0 perm 0x0
...       (0x3FFFFF7000 - 0x3FFFFFC000 identical: pte 0x0)
va 0x3FFFFFD000 pte 0x21FEC413 pa 0x87FB1000 perm 0x13
va 0x3FFFFFE000 pte 0x21FE7CC7 pa 0x87F9F000 perm 0xC7
va 0x3FFFFFF000 pte 0x20001C4B pa 0x80007000 perm 0x4B

va 0x0, perm 0x5B = V R X U A
  First page of the program's text (code, plus read-only data).
  User may read and execute it but not write it. A is set because
  the CPU has already fetched instructions (main etc.) from it.

va 0x1000, perm 0x1B = V R X U
  Second (last) page of text/rodata (the text segment is 0x158c bytes,
  so it spans two pages). Same permissions as page 0: readable and
  executable by the user, not writable. A is clear: nothing in this
  page had been touched yet when print_pgtbl ran.

va 0x2000, perm 0x17 = V R W U
  The data + bss page (global variables, e.g. testname). User may read
  and write it but not execute it (no X), so injected data cannot be
  run as code. A is clear: the globals had not been used yet.

va 0x3000, perm 0x7 = V R W (no U)
  The stack guard page. exec() allocates it and then clears PTE_U
  (uvmclear), so any user access to it traps. A stack overflow
  therefore causes a page fault instead of silently overwriting the
  data page below it.

va 0x4000, perm 0xD7 = V R W U A D
  The user stack (USERSTACK = 1 page). Readable and writable by the
  user, not executable. A and D are set because exec() wrote argv to
  it and main() has pushed stack frames onto it.

va 0x5000 - 0x9000, pte 0x0
  Not mapped. The process size is 0x5000, so nothing exists above the
  stack until the heap grows with sbrk() (malloc). Any access faults.

va 0x3FFFFF6000 - 0x3FFFFFC000, pte 0x0
  Not mapped: the gap between the heap and the special pages at the top
  of the address space.

va 0x3FFFFFD000 (USYSCALL), perm 0x13 = V R U
  The page shared with the kernel that holds struct usyscall (the pid),
  added in the "speed up getpid" part. The user may only read it: no W,
  so a process cannot fake its pid, and no X.

va 0x3FFFFFE000 (TRAPFRAME), perm 0xC7 = V R W A D (no U)
  The process's trapframe, where trampoline.S saves the user registers
  on a trap. No U, so user code cannot read or modify it; only the
  kernel (supervisor mode, while still on the user page table inside the
  trampoline) uses it. A and D are set because traps (system calls)
  have already saved registers into it.

va 0x3FFFFFF000 (TRAMPOLINE), perm 0x4B = V R X A (no U)
  The trampoline code (uservec / userret). Its physical address
  0x80007000 is inside the kernel image: it is the very same physical
  page the kernel maps at the same virtual address in its own page
  table, which is what lets the code keep running across the satp
  switch. Read + execute for the supervisor only (no U, no W).

Note that the physical addresses are not consecutive (and decrease):
each page comes from kalloc()'s free list, which hands pages out
in LIFO order, so virtual neighbours land on unrelated physical pages.

2. Walk and print a two-level page table (vmprint)
============================================================

vmprint output for the same pgtbltest process:

page table 0x0000000087f81000
 ..0x0000000000000000: pte 0x0000000021fdf401 pa 0x0000000087f7d000
 .. ..0x0000000000000000: pte 0x0000000021fdf001 pa 0x0000000087f7c000
 .. .. ..0x0000000000000000: pte 0x0000000021fdf85b pa 0x0000000087f7e000 RXU
 .. .. ..0x0000000000001000: pte 0x0000000021fdec1b pa 0x0000000087f7b000 RXU
 .. .. ..0x0000000000002000: pte 0x0000000021fde817 pa 0x0000000087f7a000 RWU
 .. .. ..0x0000000000003000: pte 0x0000000021fde407 pa 0x0000000087f79000 RW
 .. .. ..0x0000000000004000: pte 0x0000000021fde0d7 pa 0x0000000087f78000 RWU
 ..0x0000003fc0000000: pte 0x0000000021fe0001 pa 0x0000000087f80000
 .. ..0x0000003fffe00000: pte 0x0000000021fdfc01 pa 0x0000000087f7f000
 .. .. ..0x0000003fffffd000: pte 0x0000000021fec413 pa 0x0000000087fb1000 RU
 .. .. ..0x0000003fffffe000: pte 0x0000000021fe7cc7 pa 0x0000000087f9f000 RW
 .. .. ..0x0000003ffffff000: pte 0x0000000020001c4b pa 0x0000000080007000 RX

The non-leaf lines (pte ending in 01, i.e. only V set, no permission
string) are page-table pages: the root has two valid entries (one
covering va 0 - 1GB, one covering the top 1GB), each pointing to a
level-1 page, each of which points to one level-0 page holding the
leaf PTEs. vmprint shows these interior PTEs; print_pgtbl cannot,
because pgpte() always walks down to the leaf.

Leaf pages:

0x0000 RXU   text page 1 (code/rodata). Allows user read + execute;
             disallows writes, so the program cannot modify its own
             code. Same PTE (0x21fdf85b) as "va 0x0" in print_pgtbl.
0x1000 RXU   text page 2. Same permissions/reasoning; same PTE as
             "va 0x1000" in print_pgtbl.
0x2000 RWU   data/bss. Allows user read + write; disallows execute.
             Same PTE as "va 0x2000".
0x3000 RW    stack guard page. No U, so every user access is
             disallowed and faults (catches stack overflow). Only the
             kernel could touch it. Same PTE as "va 0x3000".
0x4000 RWU   user stack. User read + write; no execute. Same PTE as
             "va 0x4000".
0x3fffffd000 RU  USYSCALL page holding the pid. User may only read it;
             writes and execution are disallowed. Same PTE as
             "va 0x3FFFFFD000".
0x3fffffe000 RW  trapframe. Kernel-only (no U) read/write; the user can
             neither read nor write it. Same PTE as "va 0x3FFFFFE000".
0x3ffffff000 RX  trampoline. Kernel-only (no U) read + execute; never
             writable. Same PTE as "va 0x3FFFFFF000", and the same
             physical page (0x80007000) the kernel maps there.

Every leaf PTE value printed by vmprint is identical to the value
print_pgtbl printed for the same virtual address, since both read the
same page table of the same process. The entries print_pgtbl showed as
pte 0x0 do not appear in vmprint because vmprint skips invalid PTEs.
vmprint's virtual addresses for the top region are shown as
0x0000003f...: xv6 only uses va < MAXVA = 2^38, so they are not
sign-extended.


============================================================
3. Detect which pages have been accessed (pgaccess)
============================================================

(No written question.) Implementation notes: sys_pgaccess() in
kernel/sysproc.c. It rejects npages <= 0 or > 32768 (the bitmask for
32768 pages fills exactly one kernel page), and ranges that are not
inside the process's memory [0, sz). It validates all pages before
touching anything, builds the mask in a kalloc()ed buffer, copies it
out, and only then clears PTE_A of the reported pages (so a failing
call loses no access information), and flushes the TLB so the hardware
sets PTE_A again on the next access. A page inside sz that is not
mapped yet (lazily allocated by sbrk) is reported as not accessed; a
mapped page without PTE_U (the stack guard page) is an error.
PTE_A (bit 6) is defined in kernel/riscv.h.


============================================================
4. Speed up system calls (ugetpid)
============================================================

Which other xv6 system call(s) could be made faster using this shared
page? Explain how.

Any system call that only reads kernel state, without changing it,
can be answered from a read-only shared page, provided the kernel
keeps the copy on that page up to date:

- getpid(): done (the pid never changes, so it is written once in
  allocproc()).
- uptime(): the kernel could keep `ticks` in a single global read-only
  page mapped into every process at a fixed address; clockintr()
  already updates ticks, so it would just write it to that page too,
  and a user-level uptime() reads it with a plain load (this is how
  Linux's vDSO implements gettimeofday/clock_gettime).
- sbrk(0) (asking for the current size): the kernel could store p->sz
  in the per-process usyscall page and update it in growproc()/sbrk/
  exec, so querying the break needs no trap.
- fstat() on a file, or the parent's pid (xv6 has no getppid), could in
  principle be exported the same way, but they change more often /
  depend on more state, so the cost of keeping the page current would
  outweigh the benefit.

System calls that change state (fork, write, sbrk with n != 0, kill,
...) cannot be done this way, because the page is read-only to the user
and the work has to be done by the kernel.


============================================================
5. Use superpages
============================================================

kvmmap() now calls kmappages() (kernel/vm.c), a kernel-only copy of
mappages() that uses a 2MB level-1 leaf PTE whenever va and pa are
both 2MB-aligned and at least 2MB remain, and 4KB pages otherwise.
User page tables still use mappages() only.

How many superpage PTEs does your solution use?

95 (measured with ksupernpte(): super=95, regular=579):
  - 32 for the PLIC: 0x0c000000 - 0x10000000 (64MB / 2MB).
  - 63 for kernel data + RAM: 0x80200000 - 0x88000000 (126MB / 2MB).
The first 2MB of RAM (0x80000000 - 0x80200000) is still mapped with
4KB pages, because kernel text (R X, up to etext = 0x80008000) and
data (R W) live there with different permissions, so that range is not
2MB-uniform. The UART, VIRTIO, the trampoline and the 64 kernel stacks
(each with a guard page) are single 4KB pages, so they cannot use
superpages. That gives the 579 remaining 4KB PTEs (512 + 3 + 64).

How many bottom-level pages do these superpage PTEs save?

95 bottom-level (level-0) page-table pages, i.e. 95 * 4KB = 380KB of
page-table memory: each superpage PTE replaces one complete level-0
page-table page that would have held 512 PTEs. In terms of entries that
is 95 * 512 = 48,640 4KB PTEs that no longer exist (and, at run time,
far fewer TLB entries are needed to cover the kernel's direct map).
